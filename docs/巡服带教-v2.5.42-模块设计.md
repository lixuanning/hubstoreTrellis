# 巡服带教 v2.5.42 模块设计

> 编写人：谢志鹏　编写日期：2026-10-16　项目：巡服带教　版本号：v2.5.42
>
> 本文仅描述模块设计，不含代码实现。

## 1. 需求背景

外部预警系统（慧云预警）通过 `/vfm-verify/pipeline-batch` 批量推送预警数据，由 AI 巡检服务做二次复核。

v2.5.42 起：

- `/vfm-verify/pipeline-batch` **接收外部预警数据**，后续处理流程按「预警项配置」调整。
- **新增消费一个外部配置查询接口**：`third/warningitemconfig/queryByItemNo`（按预警项编号查询预警项基础信息，由外部对外提供）。
- 复核流程依据查询结果中的 **启用状态（enabledStatus）** 与 **是否开启二次分析（secondaryAnalysis）** 决定向下走向。

## 3. 现状流程（变更前）

`/vfm-verify/pipeline-batch` 两段式：

1. **阶段 1（同步）**：逐条按 `sampleCode` upsert 写样本表；主接口立即返回 `{ accepted, count, sampleIds, failed, message }`。
2. **阶段 2（异步，`setImmediate`）**：后台队列（并发 5 + 每条 500ms 节流）逐条 跑 LLM → 写 result → 触发回调。

**变更点**：阶段 2 执行前，需先按预警项编号查询预警项配置，再按配置决定是否执行 LLM 复核与回调。

## 4. 流程变更设计

### 4.1 变更后流程

在阶段 2 中，每条样本执行前新增「查询预警项配置」步骤：

1. 取该条样本的预警项编号 `warningItemNo`（**即入参 `checkCode`，二者为同一编号，不新增字段**）；
2. 调用 `third/warningitemconfig/queryByItemNo`（入参 `{ warningItemNo }`）拿到配置；
3. 按 `enabledStatus`（启用状态）与 `secondaryAnalysis`（是否二次分析）分支，向下走。

### 4.2 分支规则

| enabledStatus | secondaryAnalysis | 向下走向 |
| --- | --- | --- |
| 0 已停用 | —（不关心） | **仅存样本表**，不跑 LLM，不写 result |
| 1 启用中 | 1 开启二次分析 | **执行 AI 二次复核**：跑 LLM → 写 result |
| 1 启用中 | 0 未开启二次分析 | **仅存样本表**，不跑 LLM，不写 result |

> - 判定顺序：先看 `enabledStatus`，停用直接终止 LLM；启用再看 `secondaryAnalysis`。
> - **所有推送过来的数据都先写入样本表**；**result 表只存经过 LLM 的数据**，仅供 AI 识别平台内部使用，不下发下游；下游拿到的是原始样本数据用于业务处理。

### 4.3 时序（变更后，单条）

```
外部系统            /pipeline-batch        配置查询接口            后台复核
   │  POST samples      │                       │                     │
   │ ─────────────────▶ │ 写 sample（同步）      │                     │
   │ ◀───────────────── │ 立即返回 accepted      │                     │
   │                    │                       │                     │
   │                    │ ── 异步逐条 ──────────────────────────────▶ │
   │                    │                       │  查配置 warningItemNo│
   │                    │                       │ ◀─────────────────── │
   │                    │                       │ (enabled/secondary)  │
   │                    │                       │                     │
   │                    │        ┌──────────────┴─────────────┐        │
   │                    │        │ 停用           → 仅存样本表    │        │
   │                    │        │ 启用+二次分析1 → 跑LLM→写result│        │
   │                    │        │ 启用+二次分析0 → 仅存样本表    │        │
   │                    │        └────────────────────────────┘        │
   │ ◀────────────────────────── 回调整条样本数据 ───────────────────── │
```

### 4.4 大模型复核回调逻辑变更

**现状回调**

- 触发：仅 `/vfm-verify/pipeline-batch` 异步完成后触发（单条 `/pipeline` 不触发）。
- 地址优先级：`dto.callbackUrl` > `batchCallbackUrl` > `STORE_BASE_URL` + `/dm-store/ai/check/callback`。
- payload 为复核结论：

```json
{
  "result": 1,
  "uniqueId": "<sampleCode>",
  "promptTokens": 0,
  "execDuration": 0,
  "totalTokens": 0,
  "completionTokens": 0,
  "content": { "isValid": true, "confidence": 0.9, "reason": "...", "errorType": "" }
}
```

**变更后回调**

1. **换接口**：由现有回调地址，改为调用**后端提供的新接口** `POST /third/warningitemconfig/reportInfo`（告知检查项预警信息，详见第 2.3 节）。
2. **换参数**：回调参数与现状不同，改为传**整条样本数据**（而非仅结论 `content`）。下游拿到原始样本数据进行业务处理。

## 6. 已确认结论（v2.5.42）

1. **编号映射**：`warningItemNo` 与入参 `checkCode` 是同一个编号，**不新增字段**。
2. **落库与下游**：**所有推送数据都写入样本表**；**result 表只存经过 LLM 的数据**。result 表仅供 **AI 识别平台内部**使用，不下发下游；下发给下游的是**原始样本数据**，用其进行业务。
3. **查询时机与频次**：**维持**现有异步阶段查询（阶段 2 逐条执行前查配置）。
4. **鉴权**：`third/warningitemconfig/queryByItemNo` 为**内网访问**，**不需要单独鉴权**，走全局鉴权。
5. **示例编号不一致**：属示例文档粘贴问题，非接口真实行为，不作为确认项。
6. **新回调接口**：`POST /third/warningitemconfig/reportInfo`（告知检查项预警信息），请求参数为 16 个字段，见第 2.3 节。

## 7. 待确认问题

1. **回调触发范围**：只有跑 LLM 的分支回调，还是未跑 LLM 的分支（仅存样本表）也需要回调。
2. **查询失败降级**：配置查询异常（超时 / 返回异常）时，该条按「已停用跳过 LLM」处理，还是照常跑 LLM？

| 执行方 | 运维 / DBA |
